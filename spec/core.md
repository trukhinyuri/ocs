# Core contract

Edition 0.1.0-draft.1. This document and the normative documents it references define a new draft series. Existing formats with similar names need an explicit adapter and evidence for the claimed subset.

## Reading a requirement

MUST, MUST NOT, SHOULD and MAY have the meanings in BCP 14 ([RFC 2119](https://www.rfc-editor.org/rfc/rfc2119), [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174)). A SHOULD admits a documented, understood exception. Examples and reference code are informative. The [manifest schema](../schemas/manifest.schema.json) governs shape, this document governs semantics. A disagreement is a specification defect. An implementation MUST NOT use the ambiguity to grant access or perform an effect.

## Roles

A **package** is a distributable version of a component. An **instance** is an activation of a package under a particular policy and scope. An **export** is a public operation it provides. An **import** is the operation it needs. A **contract** specifies identity, version, schemas, effects and behavior. A **binding** selects a particular export and transport. A **host** admits components and mediates their use. An **executor** implements an export. A **principal** is an authenticated person, service or delegated workload. A peer host can be a caller and an executor. Language, process, machine and trust domain are independent choices.

## Packages and identity

- **C-01 Discovery.** A package directory has one UTF-8 `ocs.json` at its root. A host MUST be able to inspect its identity, exports, declared needs and binding without executing its code. Admission and enablement precede activation. A data-only package has an empty export list and a package-relative entry naming its data, instructions or view descriptor. The host reads the resource on demand. A data-only package cannot implement executable calls.
- **C-02 Identity.** The required fields are `format`, `id`, `version`, `runtime` and `exports`. Package and operation names use lowercase dotted identifiers. The spelling of a name is not proof of control over a namespace. The host MUST resolve the authenticated issuer, package ID, exact revision and trust domain before granting a binding. An account ID, resource ID, conversation ID and operation ID identify different objects. Display names and addresses MUST NOT be used as proof of identity.
- **C-03 Version.** Package and operation versions are independent SemVer strings. Core 0.1 uses exact contract versions for bindings. Deployments MAY resolve a permitted range to an exact compatible revision before the call. The common wire version is negotiated separately. Catalog data carries its own observation or revision. A published package revision is immutable.
- **C-04 Descriptor.** An export declares its operation ID, contract version, input and output schemas, and effect. The pair (operation ID, contract version) MUST be unique within a package. Imports name a contract and whether it is optional. Required imports and host features MUST resolve before the dependent function is made available. Missing optional imports disable only their dependent behavior. A host MUST report ambiguity, incompatible versions and unresolvable required activation cycles.
- **C-05 Schema.** Public schemas use JSON Schema Draft 2020-12. An implementation MAY support a smaller vocabulary for a named profile or sealed contract if it rejects other mandatory constraints before dispatch. Schema references MUST resolve from trusted, bounded inputs such as package-local resources or pinned schemas. Validation MUST NOT fetch arbitrary remote references. Validate both input and output at the trust boundary. Include a JSON Pointer where possible.
- **C-06 Extensibility.** Core members are explicitly enumerated. Names under `org.ocs` are reserved for this distribution, and the examples use the `org.example` namespace. Independent publishers choose a namespace governed by their authenticated issuer. Vendor-neutral or product-specific additions live under `extensions`, keyed by a namespaced identifier. An unknown optional extension may be skipped. An unknown required feature in `requiresFeatures` makes the affected package ineligible. An intermediary MUST preserve opaque optional data when it promises lossless forwarding. It MUST refuse conversion if an essential identity, effect, modality, precision or authorization rule would be lost.
- **C-07 Rights.** `needs` requests capabilities. Listing an export or installing a dependency never grants its use. Authority comes from the host's policy for an authenticated principal, caller package, operation, target, account, tenant and resource, as applicable. Undeclared, unbound and disallowed effects are denied before invocation. Annotations are useful for selection but do not confer privileges.
- **C-08 Lifecycle.** The host inspects → admits → binds → activates on demand → drains → releases. Pin the revision for an active call. Registered actions, subscriptions, panels and temporary grants belong to a particular instance. After disablement no new call may reach that instance. Discard late notifications from a retired generation. Release resources on normal exit, timeout or crash. If hot replacement cannot preserve state, expose the restart and recovery procedure.
- **C-09 Compatibility.** An implementation advertises only tested features of its role and binding. Additive optional behavior may be negotiated within a known version. A changed meaning, required field, effect or weaker guarantee needs a new contract version and migration. On update, review added permissions, preserve explicit routing and account identity, and distinguish reverting executable bytes from reversing data migrations.
- **C-10 Observability.** Return stable result or error semantics. Record the effective target/revision, correlation, duration and admission outcome. Diagnostics distinguish missing package, unsupported feature, denied scope, unavailable executor, invalid response and unknown write outcome. Credentials and unnecessary user content MUST NOT be logged. Policy and the actual executor determine outcome, not an extension's self-description.

## Schema resources

An embedded input or output schema is its own schema resource. A fragment-only reference in it resolves within that resource. Resolve a relative non-fragment reference against the resource’s declared base, or the package root for an embedded schema without its own base. Supply a private resolver for each pinned package. The virtual root `https://package.invalid/` maps to verified package bytes. It does not perform an HTTP request. A referenced file may use nested relative references under ordinary URI resolution. Reject an escape, ambiguous ID or unresolved required resource before exposing the affected export. The edition manifest maps each readable schema filename to its immutable UUID URN. Register that mapping locally before resolving a reference. The registry can operate offline. [Schema resources](../version.json) A sealed implementation can decline additional schema vocabularies or resource mechanisms during admission.

## Packaging and distribution

The portable development form is a directory. A supported `.ocsx` archive is a ZIP containing the same root manifest, relative package files and `ocs.sum`, a UTF-8 JSON object mapping each regular file except `ocs.sum` to its lowercase SHA-256. Entries use slash-separated relative paths. No absolute paths, empty components, dot segments, backslashes, symlinks, devices, duplicate paths or case-fold collisions are permitted. Portable archive names also exclude control characters, reserved device names, trailing spaces or dots, and reserved path punctuation. Compare names under Unicode NFC and case folding before writing to any target filesystem. Impose file count, compressed and decompressed size limits before extraction. Verify exact membership and digests before loading. Install into a fresh staging directory and switch only after verification. On failure the last admitted package stays usable.

`manifestDigest` on the wire is SHA-256 of the exact manifest bytes, not the package signature. A SHA-256 alone does not authenticate a publisher. A deployment that accepts untrusted distribution MUST verify the entire package against a trusted signature or pinned artifact digest, then make a separate permission decision. Trusted local development is an explicit policy. Installation MUST NOT run lifecycle hooks or application code. Automatic discovery MUST NOT broaden rights after an update.

A shared catalog, public registry, online license service and global coordinator are optional. A small application can pin a local package and bind one read operation. See [wire](wire.md), [composition](composition.md) and [profiles](profiles/README.md).
