# Consequential effects and durable jobs

**E-01 Classify.** An export declares `read`, `local-write` or `external-write`, and any `monetary`, `irreversible` or `destructive` flag. A host may strengthen a classification. For external writes or flagged operations, `tool.call` alone MUST NOT perform the effect. Negotiate `ocs.effects/0.1` and use the prepare/commit/readback boundary, or report that it is unavailable. A local reversible write still requires the applicable grant and preconditions.

**E-02 Prepare.** `effect.prepare` takes regular call parameters plus an idempotency key in metadata. It returns a proposal with a stable operation ID, resolved issuer, package/revision, actor, account/resource, intent digest, expiry, expected outcome and consequences (including price, affected windows and reversibility when applicable). Preparation does not apply the effect. Bind the intent to the exact operation/version and validated input. To exchange intent digests use SHA-256 over UTF-8 canonical JSON ([RFC 8785](https://www.rfc-editor.org/rfc/rfc8785)). Exclude routing trace, deadlines and display text, include all target, scope and effect-bearing parameters. Collisions of the same scoped key with different intent MUST return `conflict`.

**E-03 Authorize and commit.** The host obtains authorization for that exact digest through trusted product policy or a human surface. `effect.commit {operationId, intentDigest, meta}` uses the authority of the authenticated connection and its approval record. A caller-supplied `approved:true`, message or widget event grants nothing. Immediately before execution recheck caller/target, package pin, approval expiry, capability, current preconditions and the account's right. Denied, withdrawn, changed or expired proposals cannot run. Record intent durably before an irreversible dispatch. Reserve or serialize the same scoped key across all executing clients and replicas. A duplicate with the same intent returns the prior result, the in-flight handle or a reconciliation-required state.

**E-04 Read back.** `effect.readback {operationId, meta}` returns the authorized [effect receipt](../../schemas/profile-data.schema.json#/$defs/effectReceipt). Outcomes are `not-applied`, `applied` and `unknown`. Readback may supply provider evidence and a distinct refresh error. An applied receipt can carry a result in the original export’s output contract. Validate its data against that output schema. A large or asynchronous result can use a previously declared artifact or job return type. Read access to retained output is evaluated separately. Replaying a result cannot dispatch the effect again. Do not label an uncertain outcome as failed and retry automatically. If the downstream supports idempotency, forward a stable scoped key. A downstream without idempotency support can leave a crash between dispatch and acknowledgement unresolved. Preserve the unknown outcome until evidence or an operator resolves it. Local deduplication does not prove exactly-once external execution. Declare retention at least as long as the promised replay window. Expired records cannot make an old write safe to replay.

**J-01 Jobs (`ocs.jobs/0.1`).** An exported operation may return a [job](../../schemas/profile-data.schema.json#/$defs/job) instead of a completed business result when this return schema was declared. The owner persists the ID and access scope. `job.status {jobId, meta}` queries it. `job.cancel {jobId, meta}` requests cancellation. `job.continue {jobId, revision, input, meta}` resumes only from an applicable saved step. These controls never change the selected tenant, account, provider or principal implicitly. Jobs progress queued → running → succeeded/failed/cancelled. Running may pause for input, authority or retryable unavailability. A waiting job may return to running, or terminate. Terminal state does not reopen. A new user request is a new operation. Query state after a lost response before repeating. Use compare-and-set or an equivalent atomic reservation on competing resume requests. Keep drafts and intermediate results intact. Cancellation of a job and observed state of a remote effect are recorded separately.

**J-02 Recovery.** Multi-step jobs must define who owns each write, what is durable, and how remaining work is reconciled. Compensation is a new authorized operation with its own audit and failure states. Backup/restore or migration must preserve effect records, pending approvals and scope. A successful status read after restart alone does not prove that no duplicate effect occurred.
